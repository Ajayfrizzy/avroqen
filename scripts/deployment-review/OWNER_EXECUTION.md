1. Obtain a new explicit owner authorization for one fresh deploy/init attempt. Preserve the original attempt evidence; do not submit its signed file.
2. The owner independently provisions and secures a new empty directory. This preparation does not provide an executable directory-creation command or access that future directory.

4. Only after the new authorization, run in the owner's private Terminal:

```sh
cd ~/Desktop/avroqen
python3 scripts/deployment-review/owner-execute-testnet.py --execute-once \
  --work-dir "${new_execution_dir:?New independently secured directory required}" \
  --authorization-ref "${new_authorization_ref:?New owner authorization required}"
```

This WILL sign and submit if all checks pass and the owner confirms `AUTHORIZE NEW ATTEMPT`. Do not use it as a diagnostic or dry run. The script validates static environment/config/binary/Wasm/reference checks, secures the exclusive attempt marker, copies approved Wasm and compiles/verifies the Swift helper **before confirmation**. It prints the fixed authorized terms and warns that the earlier authorization is consumed. The authorization reference is durably recorded.

**Only after confirmation** does it fetch a fresh finalized block and construct the transaction. There is no second human prompt between that fetch and signing/submission. The fresh public hash is printed and recorded without waiting for input. Static files are rechecked after confirmation to detect changes during a long wait. A cancellation/failure leaves the directory occupied: no resume/reset/force option exists.

The script obtains a fresh finalized Testnet block, pins account/list/key queries to it, validates exactly Primary+Testing FullAccess, no code/staking, protocol88, storage10^19yocto/byte, gas10^8yocto/gas and conservative backing `(storage+366735+351)*10^19 + 0.33 NEAR`. The Testing nonce is read at that same block and incremented with an overflow check. Freshness is 120 seconds with at most 5 seconds future skew.

It constructs exactly DeployContract followed by `new({"network":"testnet"})`,100Tgas,0deposit. An independent Borsh reader verifies every field and byte-for-byte canonical reconstruction. Reference comparison derives field spans from parsing; no nonce offset is hard-coded. The public transaction hash is printed and durably recorded before signing/submission.

After fresh state and exact-byte verification, offline CLI signing uses the pinned Testing key, explicit nonce/block hash/block height, approved Wasm copied into the protected directory, and `save-to-file`. CLI stdin is closed and stdout/stderr are discarded, including errors: unexpected CLI interactive input cannot collect a secret. A macOS Keychain dialog can still appear; allow only the expected Testing item for the reviewed near executable. Never approve Primary access. There is no online auto-selection.

The resulting `signed.json` must be owner-owned, mode 0600, a regular file with no symlinks/hard links, and contain exactly the independently verified unsigned bytes plus one Ed25519 signature. A local Swift helper uses CryptoKit to verify that signature over the unsigned SHA-256 digest against Testing. It receives only public key, digest and signature over an anonymous pipe, never through arguments or logs. The helper contains no private-key/signing/Keychain API.

All live preflight checks run again. The nonce must be unchanged, the saved block must match the canonical block at its height, remain within protocol validity and the 120-second age bound, and the config/binary/Wasm/signed file must be unchanged. Any failure stops with the signed file protected; it never silently refreshes/re-signs. The script then records `04-submission-attempted.json` before invoking the exact verified signed-file submission once. CLI-internal retry behavior has not been verified by this archive correction; the single Python invocation does not prove a single internal submission attempt. The script never retries, reconstructs, re-signs or launches a second submission.

## Verification and limitations

Run preparation tests only with:

```sh
python3 -B -m unittest discover -s tests/deployment-review -p 'test_*.py' -v
```

Tests import definitions without entering the script's `__main__`. End-to-end control-flow tests mock every filesystem/preflight/subprocess boundary and clear inherited environment variables; no real near process is launched. Explicit negative tests retain the real rejection of all four prohibited custom-CA variables, including present-but-empty settings. Transport tests mock the HTTP opener: no live RPC is performed. Each read-only RPC request has a distinct ID; responses must contain exactly `jsonrpc`, `id` and an object `result`, with protocol `2.0` and the matching request ID. Errors, batches, missing/mismatched fields, duplicate JSON keys and nonfinite JSON constants fail closed. Filesystem tests use separate disposable directories, not the owner deployment directory. CryptoKit is compiled and tested only with a published Wycheproof public verification vector (tc84), plus altered signature/digest/framing. No signature or private key is generated. The revised script's live entrypoint, owner config, original attempt directory, any future execution directory and real signer remain untested/unaccessed by this preparation. Regression tests simulate a ten-minute confirmation wait before state fetch, expiry after signature verification with no submission checkpoint, changed chain state/nonce, wrong signer, interrupted signing/submission and repeated execution blocked by exclusive markers.

This is a local self-review, not an independent security audit. Same-user malware or an administrator can race file replacement or change the binary/config after checks; the script cannot secure a compromised host. It checks ownership/modes, symlinks, inode identity, exact hashes and unchanged bytes, but those are not a hardware custody boundary. Swift/Python may leave signature copies in memory; the script disables core dumps but does not guarantee forensic erasure. The retained signed file is executable authorization and stays protected for unknown-outcome investigation. Blockchain state can change after final preflight; no code can make public RPC and later submission atomic. Such failures must be investigated, never retried automatically. Owner intervention may be required if Swift/compiler setup or conservative configuration validation fails. These offline tests make no claim of public-chain success; the separate linked deployment record describes only the owner-provided verified evidence.
